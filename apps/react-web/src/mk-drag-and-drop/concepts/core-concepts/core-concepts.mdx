# Core concepts

## Ownership

The package owns pointer and keyboard input, target measurement, targeting,
modifiers, overlays, package-owned sortable preview DOM, normalized lifecycle
events, and cleanup. Applications own markup, styles, canonical models, visible
projection outside the sortable carriers, and one final commit.

Registration describes what exists. Lifecycle describes one drag. Neither is
an application transaction system.

## Scope

A DOM controller creates one drag-and-drop scope. In React, one `DragProvider`
creates one scope and hooks read the nearest provider. Nested providers create
isolated scopes. Coordination across nested providers is not a special public
feature.

Use a single provider for related domains and separate them with groups:

```tsx
<DragProvider onDragUpdate={routeByGroup}>
  <DocumentBlocks />
  <SortableTable />
</DragProvider>
```

## Groups

Groups are both target-interaction boundaries and lifecycle-routing
identifiers. Only targets in the captured group can interact with the active
drag.

```ts
switch (event.group) {
  case "document-blocks":
    break;
  case "table-rows":
    break;
  case "table-columns":
    break;
}
```

The group is captured when activation succeeds and is immutable for the drag.
Registration changes can invalidate the source or target but cannot change
event or announcement routing. Keep `draggableId` a stable logical identity;
do not encode domain routing into it.

## Draggables, targets, and sortables

- A draggable is a drag source.
- A droppable is a target.
- A drop container is a target region for container placement, including empty
  destinations.
- A sortable combines a source and item target and participates in transient
  preview ordering.

`activeDropTargetId` reports selection. Sortable before/after placement is
already represented by `sortablePreview`; do not calculate it from the target
id.

## Canonical and projected state

The application canonical model does not change during `onDragUpdate`.
`SortablePreview` drives optional local presentation:

```text
canonical model -- source/inactive --> canonical visible order
DragUpdateEvent.sortablePreview -- projected --> transient visible order
DropEvent.sortablePlacement --> one canonical commit
```

The package restores its sortable preview nodes before public end/drop
callbacks. Application projection is cleared on non-dropped end, or after the
successful drop callback commits.

## Activation and handles

Pointer activation delay and distance use OR semantics. Reaching either
configured threshold activates. Releasing quickly before activation remains an
ordinary click. An activated pointer drag suppresses at most the related
generated click in the initiating draggable subtree; later unrelated,
programmatic, and keyboard clicks work normally.

A descendant button may be the pointer handle. Space and Enter remain reserved
for button/menu activation and do not start keyboard drag through an interactive
button. Keyboard sorting needs a separate noninteractive or separately focusable
handle, or explicit commands. Editable descendants are always protected.

## Completed events

Every normal update includes `group` and discriminated `sortablePreview`. The
package selects a target, applies its preview mutation, normalizes that current
order, and then publishes. Adapter/runtime subscribers and public callbacks
receive the same completed event.

Live and drop placement share `SortableDropPlacement`; there is no second
placement representation. A source/no-op successful drop omits final placement.
